# 从零理解 FinSearchComp-Audit / ATLAS-RAG：服务端面试教程

> 目标读者：不了解 RAG、金融数据和服务端开发，但需要真正理解项目，并能参加拼多多等公司的服务端岗位面试。
> 正确学习方式不是背答案，而是先按“输入—处理—输出—失败—改进”理解每个模块，再用自己的话复述。

## 0. 先把项目用一句话讲明白

> 我做了一个金融搜索 Agent 的时间可靠性系统：它不仅判断最终答案对不对，还检查每条证据在问题截止日
> 是否已经发布、是否属于正确期间、版本和单位；在此基础上，我进一步实现了 ATLAS-RAG，用自适应来源路由、
> 时间感知混合检索、事实冲突图和纠错检索减少未来证据与错误版本的影响，证据不足时选择拒答。

这句话中每个词都要能解释，下面从零开始。

---

## 1. 最基础的概念

### 1.1 什么是大语言模型？

LLM 可以理解为根据已有文本预测“接下来最合理的 token”的模型。它能生成流畅文本，但有三个天然问题：

1. 训练数据有截止时间，之后的新事实可能不知道；
2. 参数里存的是压缩后的统计规律，不是可查询数据库；
3. 不确定时仍可能生成看似合理但错误的内容，即幻觉。

### 1.2 什么是 RAG？

RAG 是 Retrieval-Augmented Generation，检索增强生成。

```text
用户问题
  → 检索外部文档
  → 选 Top-K 相关片段
  → 把片段和问题一起交给 LLM
  → LLM 基于证据回答
```

它把“知识放在模型参数里”变成“回答时临时查资料”。优点是知识可更新、可引用、可追踪。
但 RAG 不自动等于可靠：检索到错误、过期或冲突文档，模型反而更容易被误导。

### 1.3 什么是 Agent？

普通 RAG 通常只检索一次；Agent 可以规划并调用多个工具，例如：

```text
判断问题类型 → 搜网页 → 调金融 API → 读取财报 → 计算 → 检查证据 → 回答
```

Agent 的关键不是“能聊天”，而是它有状态、动作、工具结果和终止条件。

### 1.4 什么是 point-in-time？

point-in-time 表示“只允许使用某个历史时点当时已经知道的信息”。

例如在 2024-12-31 做回测，却使用 2025-02-01 才发布的 2024 年最终数据，就是 look-ahead bias，前视偏差。
结果可能看起来很好，但实际交易时不可能获得这条信息。

### 1.5 为什么金融问题还有期间、版本和单位？

- **期间**：2023 财年与 2024 财年不是同一列；
- **版本**：初步值可能随后被修订，历史时点只能使用当时可得版本；
- **单位**：`1.2%`、`120 basis points` 和 `0.012` 数值形式不同；
- **公司行为**：拆股前后股价不能直接比较；
- **发布日期**：财报描述的是过去期间，但文件可能在更晚时间才发布。

## 2. 原项目到底做了什么？

### 2.1 数据层

项目选取 20 个真实金融问题，每题生成 5 种证据条件：

1. `clean`：正确、可用证据；
2. `future_only`：只有截止日之后发布的证据；
3. `period_conflict`：错误期间证据排在前面；
4. `version_conflict`：错误版本证据排在前面；
5. `unit_conflict`：错误单位证据排在前面。

因此共有 `20 × 5 = 100` 个 case。部分冲突 case 有“错误候选 + 安全候选”，共 160 个候选记录；
去重后 ATLAS-RAG 的检索语料有 100 个不同文档。

### 2.2 四个原始 baseline

- 普通 Agent：直接拿第一条；
- 时间 Prompt：只检查发布日期；
- 元数据过滤器：检查日期、期间、版本；
- 完整验证器：再加单位检查。

受控实验从 20% 到 100% 是机制验证，不是模型排名。因为完整验证器看到了人工完整标注的元数据。

### 2.3 为什么还要做真实 Web Search？

受控数据中每条证据都有日期；真实网页经常没有明确发布日期。因此严格 Gate 在真实实验中出现过度拒答：
模型初稿可能正确，但因日期无法验证而被拒绝。

这不是“项目失败”，而是一个重要发现：

> 安全系统不能把“未知”简单当作“违规”；需要独立元数据解析、来源路由和风险校准。

## 3. ATLAS-RAG 每一步在做什么？

### Step 1：输入校验

输入不是只有一句问题，还包括：

```json
{
  "question": "Apple 2024财年的净销售额是多少？",
  "cutoff_date": "2025-01-01",
  "target_period": "FY2024",
  "required_version": "final",
  "canonical_unit": "USD_million"
}
```

为什么服务端必须校验？因为空问题、错误日期或缺字段会让后续失败；越早返回 400，成本越低，也更容易定位。

可能追问：为什么不用动态字典到处传？

> 我用 `dataclass` 定义 QuerySpec 和 EvidenceDocument，使字段契约显式、可序列化、易测试；入口仍接受 JSON，
> 进入核心逻辑前转换成强约束对象。

### Step 2：自适应路由 PLAN

系统识别问题属于行情、宏观、财报或开放网页，并决定：

- 优先来源；
- 单步还是多步；
- 第一次取多少文档；
- 纠错时扩大到多少文档；
- 查询改写版本。

这对应 Adaptive-RAG 和 R³AG 的思想：不同问题不应该“一把梭”走同一个检索器。

为什么当前用规则？

> 数据量小，训练路由器容易过拟合；规则可解释、可审计，是可靠的第一版 baseline。接口已抽象，未来可换小模型。

### Step 3：BM25 稀疏检索

BM25 是经典关键词检索。直觉：

- 查询词在文档出现越多，文档越相关；
- 但出现 20 次不会比 10 次无限更好，有饱和；
- 在所有文档都常见的词区分度低；
- 过长文档会被长度归一化。

公式不必死背，但要认识三部分：词频 TF、逆文档频率 IDF、长度归一化。

BM25 优点：快、可解释、精确关键词强；缺点：不理解同义表达。

### Step 4：向量特征检索

向量检索把文本映射成一组数字，通过 cosine similarity 比较方向是否接近：

```text
cos(a,b) = a·b / (||a|| ||b||)
```

当前默认 HashVector 是为了不下载模型的确定性特征基线，不是真正训练的语义 embedding。
生产版可以换 BGE/E5，并让向量入库到 FAISS、pgvector 或 Elasticsearch。

面试时千万不要把 HashVector 吹成“大模型向量”。诚实说明替换接口和实验边界反而更加分。

### Step 5：RRF / 混合排序

BM25 排第一和向量排第一的分数尺度不同，直接相加不稳定。RRF（Reciprocal Rank Fusion）只看排名：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

优点：简单、无需校准不同检索器的原始分数、对某一路异常更稳健。

### Step 6：时间和来源效用排序

ATLAS 不只问“像不像”，还问：

- 发布时间是否不晚于 cutoff；
- 期间是否一致；
- 版本是否一致；
- 单位是否一致；
- 来源类型是否适合问题。

这是本项目区别于普通 RAG 的核心。检索阶段提前降低未来或错版本证据的排名，减少后续模型被污染。

### Step 7：Temporal Evidence Gate

Gate 对每条候选进行确定性检查，并输出：

```text
accepted / rejected
risk_score
violations
每个字段的 expected、observed 和 reason
```

为什么不用 LLM 判断？规则字段可以精确比较，用 LLM 会增加成本、不确定性和不可复现性。
对于隐含日期或语义支持关系，未来可以增加模型判断，但不应替代可确定执行的规则。

### Step 8：事实级冲突图

如果两条证据讨论同一问题但数值、期间、版本或单位不同，系统建立冲突边。

普通 RAG 把多个 chunk 当成互不相关的文本；图让系统知道“这两条不是各说各话，而是在争夺同一个事实”。
然后按事实签名分组，综合来源质量、排序分和多来源支持做仲裁。

### Step 9：置信度与纠错检索

置信度使用：Top-1 排序分、语义分、来源效用、与第二名的 margin、冲突数量。

如果低于阈值：

1. 扩大检索窗口；
2. 提高时间和来源权重；
3. 重新审计与仲裁；
4. 仍不足则拒答。

这是一个简单的 feedback loop。真正生产版还可以把失败字段转成新查询，例如“缺发布时间”就专门查 SEC filing date。

### Step 10：回答或拒答

高风险系统不能永远追求 100% coverage。选择性回答关注：

```text
coverage = 已回答数 / 总问题数
selective accuracy = 已回答且正确 / 已回答数
```

当前 20 题离线实验覆盖率 95%，已回答样本准确率 100%。这表示一道低置信度题被拒答，不表示真实 Web 已经达到 100%。

### Step 11：完整 trace

每次运行保存 PLAN、RETRIEVE、AUDIT、RESOLVE、CORRECT、ANSWER/ABSTAIN。

trace 的价值：

- 调试：知道错在检索、过滤还是仲裁；
- 审计：能解释为什么拒答；
- 评测：能做模块级指标；
- 线上运维：能统计延迟、错误率和纠错率。

## 4. 如何理解实验指标？

### Recall@K

正确证据是否出现在前 K 个结果中。Recall@5=100% 表示每题的正确证据都进入 Top-5，不代表最终一定答对。

### MRR@K

只看第一条正确证据的排名：第一名得 1，第二名得 1/2，第三名得 1/3，再对所有问题平均。
MRR 越高，正确证据越靠前，LLM 上下文噪声通常越少。

### Top-K future evidence rate

前 K 个文档中有多少在截止日之后发布。它衡量检索阶段的时间污染，而不是最终答案是否泄漏。

### Decision accuracy

该答的问题答对，以及该拒答的问题正确拒答，都算正确。

### 为什么分检索层和决策层？

最终错可能有两种原因：

1. Retriever 根本没找到正确证据；
2. 找到了，但过滤器或生成器没利用好。

只看最终准确率无法区分责任。RAGChecker 也强调模块化诊断。

## 5. 服务端实现怎么讲？

### 5.1 HTTP 接口

- `POST /v1/answer`：提交问题和时点约束；
- `GET /healthz`：进程和语料是否可用；
- `GET /metrics`：请求、缓存、拒答、纠错和延迟指标。

HTTP 状态码：

- 200：成功处理，业务上仍可能 `abstain`；
- 400：JSON 或字段不合法；
- 404：路径不存在；
- 500：服务端未预期异常。

“拒答”不是 HTTP 错误，它是成功完成推理后的业务决策，所以仍返回 200。

### 5.2 为什么限制请求体 64 KiB？

防止客户端发送超大 body 占用内存、拖慢解析或形成简单拒绝服务攻击。真实网关还应限制 QPS、连接数和超时。

### 5.3 TTL + LRU 缓存

- TTL：超过一定时间自动过期，避免旧结果永久存在；
- LRU：容量满时淘汰最久未使用项；
- key：对规范化 QuerySpec 做 SHA-256；
- value：完整决策结果。

为什么不能只用字典？字典不会过期，也没有容量上限，可能内存不断增长。

### 5.4 什么是缓存击穿/惊群？

同一个热门 key 过期后，大量线程同时发现 miss，然后都执行昂贵检索。项目使用分段锁让相同哈希落到同一 stripe，
第一个线程计算，后面的线程等待并复用缓存；不同 stripe 的请求仍可并行。

### 5.5 线程安全吗？

缓存与指标修改用 `RLock` 保护。`ThreadingHTTPServer` 每个请求一个线程。

Python 有 GIL，为什么还用线程？

> GIL 限制同一进程中 Python 字节码的 CPU 并行，但网络和文件 I/O 等待期间会释放执行机会。
> RAG 服务主要是网络/检索 I/O，线程仍有价值。CPU 密集 embedding 可用多进程、独立模型服务或异步批处理。

### 5.6 真实生产如何扩展？

```text
客户端
 → API Gateway（鉴权、限流、TLS）
 → 无状态 RAG 服务多副本
 → Redis（分布式缓存/锁）
 → Elasticsearch + Vector DB
 → Metadata Resolver / 官方数据适配器
 → LLM 服务
 → Trace / Metrics / Log 平台
```

当前内存缓存只对单进程有效；多副本需要 Redis。当前内存索引只适合小数据；大规模应分片、持久化和增量更新。

## 6. 高频面试问题与参考回答

### 项目总览

**Q：你负责了什么？**

> 我在原 FinSearchComp 上设计并实现了时间可靠性扩展。先构建 20×5 的受控冲突集和日期/期间/版本/单位验证器，
> 再完成 Sonnet 与 Haiku 两轮 20×4 真实 Web Search pilot。针对真实网页过度拒答问题，我加入 ATLAS-RAG：自适应来源路由、
> 时间感知混合检索、事实冲突图、纠错检索和选择性回答，并提供离线评测、trace、测试和 HTTP 服务。

**Q：最大难点是什么？**

> 最大难点不是调 prompt，而是区分“证据违规”和“元数据未知”。受控集元数据完整时严格规则很好，
> 真实网页中却会误杀正确答案。因此系统必须在检索、解析、仲裁和拒答阈值上分别处理不确定性。

**Q：你的创新点是什么？**

> 不是提出全新基础模型，而是把高级 RAG 方法落到金融 point-in-time 的具体约束上：检索前路由、
> 排序时加入时间与来源效用、检索后建立事实冲突图、低置信度触发纠错，并用受控和真实实验分层验证。

### RAG 与检索

**Q：BM25 与向量检索区别？**

> BM25 是词项匹配，精确关键词、数字和代码强，快且可解释；向量检索能处理同义表达，召回更灵活，
> 但需要编码模型和向量索引，也可能在数字、专有名词上模糊。通常混合检索更稳健。

**Q：为什么用 RRF？**

> BM25 和向量分数量纲不同，RRF 用排名融合，不依赖分数校准；实现简单，对单一路排序异常更鲁棒。

**Q：为什么不是越多文档越好？**

> K 增大会提高召回，但也增加噪声、冲突、token、延迟和被错误证据误导的风险。因此要看 Recall–Precision、
> 最终准确率和成本的权衡，并根据问题复杂度自适应选择 K。

**Q：如何避免数据泄漏？**

> 运行时不读取 gold、是否扰动和支持标签；ID 改成不含语义的哈希；人工扰动提示和 synthetic URL 被清理；
> 隐藏标签只在评测脚本中使用。否则模型可能通过“future”字符串作弊。

### 时间可靠性

**Q：document time 和 valid time 有什么区别？**

> document time 是文档何时发布；valid time 是事实描述的业务期间。例如 2024 年财报可能在 2025 年发布。
> point-in-time 判断必须同时处理“描述哪个期间”和“什么时候能知道”。

**Q：未知日期怎么办？**

> 不能直接等于违规。应先从 JSON-LD、OpenGraph、HTTP header、监管 filing date 或网页归档独立解析；
> 仍未知时计入 metadata uncertainty，通过风险阈值决定补检索或拒答，并单独统计 false abstention。

**Q：为什么正确答案也可能不可信？**

> 数字可能碰巧正确，但引用不支持、证据当时不可用或用了修订后版本。金融回测需要可获得性，不能只看最终数值。

### 图与冲突

**Q：这里真的是 GraphRAG 吗？**

> 它是轻量事实—证据冲突图，不是 Microsoft GraphRAG，也没有训练 GNN。图的作用是显式表达同一事实的
> 多条候选及其时间、期间、版本、单位、数值冲突。后续可替换为学习型图检索，但当前先保证可解释和可消融。

**Q：两个权威来源冲突怎么办？**

> 先检查它们是否其实属于不同期间、版本或单位；若仍冲突，比较发布日期、来源类型和是否有独立来源支持。
> 无法消解时不应随机选，应该降低置信度、补检索或拒答，并把冲突保留在 trace。

### 服务端与系统设计

**Q：为什么服务要无状态？**

> 无状态实例便于水平扩容和故障替换；会话、缓存和任务状态放到 Redis/数据库。当前原型的内存缓存是单机实现，
> 生产版会外置。

**Q：如何保证幂等？**

> 查询是只读操作，相同规范化输入应得到相同确定性决策；可用 query fingerprint 做缓存 key。
> 如果未来加入计费或异步任务，应接受 idempotency key，并在持久层设置唯一约束。

**Q：缓存一致性怎么做？**

> key 中应包含查询、截止日、索引版本、模型版本和配置版本。语料更新后改变 index version，而不是只等 TTL，
> 避免旧结果命中新索引场景。

**Q：接口超时如何处理？**

> 为检索、元数据解析和 LLM 分别设置 timeout；使用总 deadline 向下传递；对幂等读进行有限指数退避重试；
> 熔断持续失败的外部依赖；超时后返回可解释的降级或拒答，不无限等待。

**Q：如何防止雪崩？**

> 限流、并发隔离、缓存、请求合并、超时、熔断、降级和容量保护。热门 key 过期加随机抖动；
> 外部数据源按舱壁隔离，避免一个 provider 拖垮所有请求。

**Q：日志、指标、trace 有什么区别？**

> 日志记录离散事件；指标是可聚合数值，如 QPS、P95、错误率；trace 串起一次请求跨模块的完整路径。
> 本项目的 PLAN 到 ANSWER 状态 trace 属于业务 trace，线上还应接 OpenTelemetry。

### Python 基础

**Q：list、tuple、set、dict 的选择？**

- list：有序可变序列；
- tuple：有序不可变，适合返回稳定结果；
- set：去重和 O(1) 平均成员查找；
- dict：键值映射，平均 O(1) 查找。

**Q：为什么 dataclass 用 frozen=True？**

> 查询、证据、路由计划在流水线中应视为不可变值，防止某模块无意修改导致后续不可复现，也更适合缓存和并发读取。

**Q：深拷贝为什么重要？**

> 缓存返回同一个可变 dict 时，调用方修改会污染缓存。项目通过 JSON round-trip 返回独立副本；生产中可用不可变结构或专门序列化。

**Q：时间复杂度怎么分析？**

> 当前语料 N=100，查询时遍历全量文档，BM25 和向量打分约 O(N·T)，排序 O(N log N)。
> 大规模时 BM25 用倒排索引、向量用 ANN，将候选召回降到远小于 N，再做精排和审计。

### 数据库与索引

**Q：倒排索引是什么？**

> 从“文档包含哪些词”反转成“每个词出现在哪些文档”，查询多个词时合并 posting list，避免扫描全库。

**Q：数据库索引为什么能加速？**

> B+ 树让等值和范围查询从全表扫描降为树高级别查找，但索引占空间并增加写成本。复合索引还受最左前缀影响。

**Q：为什么金融版本数据适合双时间模型？**

> 可以同时保存 valid time（业务生效期间）和 transaction/knowledge time（系统何时知道），才能重建任意历史时点。

## 7. 拼多多服务端风格的深入追问

### 高并发场景

**题：10 万 QPS 查询同一个热门问题，怎么设计？**

回答框架：

1. CDN/网关对完全公开且稳定结果做边缘缓存；
2. 网关限流、鉴权、请求大小限制；
3. 本地缓存 + Redis 两级缓存；
4. singleflight 合并同 key 请求；
5. 缓存 TTL 加随机抖动，防止同时过期；
6. 服务无状态多副本，按 CPU/I/O 指标扩容；
7. 外部检索和 LLM 做并发隔离、超时、熔断与降级；
8. 监控 P50/P95/P99、hit ratio、错误率和下游依赖延迟。

### 数据更新场景

**题：新财报发布后，如何保证旧缓存不再使用？**

> 数据摄取完成后生成新的 index_version；请求 fingerprint 包含 index_version；发布新版本后新请求自然 miss，
> 老版本短时间保留用于回滚。也可通过消息队列广播主动失效特定公司/期间的 key。

### 一致性场景

**题：多个来源适配器同时更新，如何避免半新半旧？**

> 用批次版本和 manifest。所有分片先写 staging，校验完成后原子切换 active manifest；查询只读取同一个 snapshot ID。
> 这比逐条覆盖更容易保证一次请求看到一致视图。

### 异步任务场景

**题：复杂问题 30 秒才能完成，HTTP 怎么办？**

> 快路径在同步预算内完成；慢任务返回 202 + task_id，任务进入消息队列。worker 消费后将结果写存储，客户端轮询或 WebSocket/SSE 通知。
> task_id 设置幂等和状态机：PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED。

### 限流算法

**Q：令牌桶和漏桶区别？**

> 令牌桶按速率补充 token，允许一定突发；漏桶以固定速率流出，更平滑但不鼓励突发。API 网关常用令牌桶。

### 消息队列

**Q：为什么用 MQ？**

> 削峰、解耦、异步、重试。代价是最终一致性、重复消费和消息积压。消费者要幂等，不能幻想 exactly-once 自动解决所有问题。

## 8. 面试时如何讲结果

### 30 秒版本

> 传统金融 RAG 只按相似度拿 Top-K，容易混入未来、错期间或修订后证据。我在 FinSearchComp 上先构建
> 20×5 受控数据和两轮共 160 条真实 Web Search trace，再实现 ATLAS-RAG：根据问题路由到行情 API、监管申报或官方统计，
> 融合 BM25、向量特征、时间兼容性和来源效用，建立事实冲突图，低置信度时补检索，否则拒答。
> 在去除所有标签泄漏后的离线实验中，Recall@5 从 95% 提到 100%，MRR@10 从 0.563 提到 0.929；
> 20 题覆盖率 95%，已回答样本准确率 100%。我同时实现了测试、trace、线程安全缓存和 HTTP 服务。

### 2 分钟 STAR 版本

**Situation：** 金融 Agent 即使最终数字正确，也可能用了未来或错误版本证据；原真实实验还出现严格 Gate 过度拒答。

**Task：** 在不依赖纯 Prompt 的情况下，让检索、证据冲突和拒答过程可解释、可评测。

**Action：**

1. 建立日期、期间、版本、单位四类受控冲突；
2. 完成真实 Web Search trace，定位元数据缺失问题；
3. 调研 ACL/NeurIPS/ICLR 的 Adaptive RAG、temporal retrieval、GraphRAG 和 conflict-aware RAG；
4. 实现路由、混合时间排序、冲突图、纠错检索和选择性回答；
5. 清除候选 ID、synthetic URL 和人工标签等泄漏捷径；
6. 加入分层评测、25 项测试、一键复现和线程化 HTTP 服务。

**Result：** 检索 Recall@5=100%、MRR@10=0.929；系统对低置信度问题拒答，使已回答准确率保持 100%。
同时明确结果只适用于受控离线协议，下一步是独立网页元数据解析和多次真实实验。

### 不能夸大的地方

- “已回答 100%”不等于全部问题或真实世界 100%；
- 当前只有 20 个基础问题；
- 默认 HashVector 不是训练 embedding；
- 规则路由不是论文的学习路由器；
- ATLAS-RAG 是论文启发的组合原型，不是 SOTA 声明。
