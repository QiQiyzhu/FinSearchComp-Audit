# FinSearchComp-Audit：3 分钟演示稿

## 演示目标

三分钟内明确四件事：

1. 研究问题不是“再做一个金融聊天机器人”；
2. 本项目检查金融 Agent 的证据是否满足时间、期间、版本和单位约束；
3. 目前已有 100 条受控实验、四个策略、指标和逐证据 trace；
4. Claude 的 10题×4策略真实 pilot 已完成，共 40 条严格验证 trace。

## 第 1 页：GitHub README（约 45 秒）

打开：

<https://github.com/QiQiyzhu/FinSearchComp-Audit>

可以直接说：

> 现有金融 Agent Benchmark 主要检查最终答案是否正确，但金融问题还有一个特殊风险：
> Agent 可能使用问题截止日之后发布的信息，或者混用错误期间、修订版本和金额单位。
> 我的项目是在答案正确率之外，增加一个时间可靠性审计层。

指出 README 顶部的 100 条受控实验表，但马上补充：

> 这里的 100% 是受控协议的设计上限，不是真实 LLM 排名。我保留这个边界；
> 下方 10×4 真实 Web Search pilot 专门检查外部有效性，而且结果并没有复制这个 100%。

## 第 2 页：时间可靠性实验（约 75 秒）

打开：

<https://qiqiyzhu.github.io/FinSearchComp-Audit/temporal-audit.html>

讲解四类人工冲突：

- 未来证据：发布时间晚于问题截止日；
- 错期间：例如题目问 2023 财年，证据来自 2024 财年；
- 错版本：初步值、修订值或最终值混用；
- 错单位：百分比、基点、百万美元等口径不一致。

可以直接说：

> 普通 Agent 在受控挑战条件下会采用所有扰动证据。只加时间 Prompt 有改善，
> 但不能处理期间、版本和单位冲突。元数据过滤器进一步提升，而完整证据验证器
> 对四类字段逐一检查，并在没有安全证据时拒答。

解释 TRG：

> Temporal Robustness Gap 是干净条件准确率与挑战条件准确率的差值。
> 越接近零，说明方法面对受污染证据时越稳定。

## 老师可能追问

### 为什么先发布 10 题 × 4 策略？

先用 1 题检查模型权限、搜索引用格式、发布日期字段和费用，再逐步扩大。本轮在停止时
已有前 10 道题四策略完整，因此公开这 40 条公平配对结果；第 11 题只有两种策略完成，
已记录但不混入比较。受控实验与真实 pilot 分别回答机制有效性和开放网页外部有效性。

Claude 因为 citations 与 Structured Output 不能同一请求启用，所以每个策略固定为
同一模型、同一 effort 的“搜索研究 + 结构化归一”两个阶段。当前 40 条公开记录对应
80 个成功 HTTP 阶段、70 次 Web Search；完整 20×4×3 仍只是未来设计。

### 100 条数据是不是太少？

这是第一版 mini benchmark，用于验证任务定义、扰动设计和指标是否有效。
投稿版本需要扩大问题、领域、来源和模型覆盖，并做人工一致性检验。

### 完整验证器为什么能达到 100%？

因为当前受控集的日期、期间、版本和单位都有明确标注。这个结果说明规则实现正确，
不等于开放网页中的所有元数据都能自动获得。

### 与 Look-Ahead-Bench 有什么区别？

Look-Ahead-Bench 关注金融模型或策略在不同时期的前视偏差；本项目把问题推进到
金融研究 Agent 的检索链路，检查每条证据在问题指定时间点是否可用。
